EC2 deployment with GHCR

New instance deploy flow: build images once into GitHub Container Registry, then pull a tagged image onto any EC2 — secrets stay in the machine-local .env files, not in the image.

Mental model

CI builds the app once and pushes simstudio, realtime, and migrations to GHCR. On the instance you only pick a tag (or build locally for a one-off). Compose loads apps/sim/.env and apps/realtime/.env automatically — you do not bake env into the image and you do not re-export secrets by hand for each deploy.

How GHCR fits in

GHCR (GitHub Container Registry) is GitHub’s Docker registry at ghcr.io. Packages live under the repo owner, tagged like any other container image. EC2 authenticates with a PAT / GHCR_TOKEN, pulls the three images for that tag, and starts them with Compose.

Published packages (same tag across all three)
ghcr.io/arenadeveloper02/p2-sim-simstudio:<tag> ghcr.io/arenadeveloper02/p2-sim-realtime:<tag> ghcr.io/arenadeveloper02/p2-sim-migrations:<tag>

Compose file: docker-compose.test-env.yml · default tag fallback: dev

1 Build in CI

GitHub Actions builds linux/amd64 images from the Dockerfiles.

2 Push to GHCR

Tags land on ghcr.io/arenadeveloper02/p2-sim-* packages.

3 Pull on EC2

deploytag.sh logs in (optional token), pulls, and ups Compose.

4 Inject env

Compose mounts env_file from apps/sim and apps/realtime .env.

Build and push images

Trigger .github/workflows/images.yml for a branch and tag. That builds and pushes all three images. Tags are immutable: the workflow creates a matching GitHub git tag ghcr/<image_tag> and refuses to republish if that git tag or the GHCR Docker tag already exists.

Immutability

Docker tag fix-prod-secrets-0.0.2 is locked by git tag ghcr/fix-prod-secrets-0.0.2 at the built commit. A failed run deletes the reservation so you can retry the same tag; a successful run keeps it forever — bump the tag for the next build.

Auto-increment tags like 0.0.N still come from pushes to the production image branch via CI (scripts/ci/ghcr-next-branch-tag.sh). Manual runs from this page (or gh workflow run) publish an explicit immutable tag.

Deploy on any instance

On each EC2 box the operators use short aliases that wrap the repo scripts. Both paths end on the same Compose file; only the image source differs.

Image pull (GHCR) Preferred

Use when the image already exists in GHCR. Fastest path for shared / stable deploys.

Instance alias
./deploytag.sh <tag>
Repo script
scripts/deploy-ec2-ghcr.sh
Run on the EC2 instance (tag-only)
./deploytag.sh fix-prod-secrets-0.0.2
Optional branch override
./deploytag.sh fix-prod-secrets-0.0.2 fix/prod-secrets
What it does

1. Checkout git lock tag ghcr/<tag> (exact build SHA). Optional 2nd arg overrides with a branch.

2. Require apps/sim/.env and apps/realtime/.env.

3. docker login ghcr.io when GHCR_TOKEN or CR_PAT is set.

4. pull simstudio, realtime, migrations for IMAGE_TAG.

5. compose up -d, then wait for :3002/health and :3000.

Local build on the box Dev / hotfix

Use for branch experiments when you do not want to wait on GHCR, or the image is not published yet.

Instance alias
./deploylocally.sh <branch>
Repo script
scripts/deploy-ec2-local-build.sh
Run on the EC2 instance
./deploylocally.sh fix/prod-secrets
What it does

1. Stop/remove old p2-sim-simstudio and p2-sim-realtime containers/images.

2. Checkout and rebase the requested branch under DEPLOY_ROOT.

3. Require apps/sim/.env.

4. compose -f test-env -f local-build up -d --build.

5. Builds from docker/app.Dockerfile and docker/realtime.Dockerfile on the instance.

Why you do not bake env into the image

Images are environment-agnostic artifacts. Runtime config comes from files already on the instance. That means one GHCR tag can be deployed to multiple boxes without rebuilding, as long as each box has its own .env.

simstudio
env_file
apps/sim/.env

Compose also substitutes selected keys (DATABASE_URL, auth URLs, API keys, etc.) via --env-file apps/sim/.env passed by the GHCR deploy script.

realtime
env_file
apps/realtime/.env

Required by deploy-ec2-ghcr.sh. Same pattern: container receives the file at start; no rebuild when secrets change — edit .env and re-up.

Practical implication

Publish the image once (UI form or gh workflow run images.yml), keep secrets only on the instance, then run ./deploytag.sh <tag> (checks out ghcr/<tag> + pulls the matching images). Changing env does not require a new image; changing code needs a new immutable tag — never reuse a published one.
